# M1 — Onboarding and patient access

## Scope

M1 implements the ROADMAP onboarding slice: patient profiles, clinical care-team membership, caregiver contacts, explicit caregiver dashboard permission, Patient 360 shell, onboarding timeline, and an optional read-only patient dashboard. It uses local synthetic identities and data.

Patient messaging, monitoring submissions, uploads and acknowledgements use WhatsApp. Patients may optionally use the web dashboard to view their own details and history. Care plans, message simulation, observations, clinical alerts, and compliance/emergency policies are outside M1.

## Role boundaries

| Role | Patient visibility | Mutations |
| --- | --- | --- |
| ADMIN | All patients in own organization | Profiles, care teams, caregivers and access within the tenant |
| DOCTOR / PA_COORDINATOR | Actively assigned care-team patients | Can onboard new patients; edit assigned patients and their memberships/access |
| CAREGIVER | Active caregiver profile/account + active patient link + dashboard grant | Read only; no profile, membership, directory or permission writes |
| PATIENT | Only the one patient record explicitly bound to their identity | Read only; own profile, care-team names and patient-facing history |

The treating doctor and a doctor/PA creating a patient are automatically assigned. A PA can onboard a patient with a selected treating doctor. Shared caregiver profile edits affect all active patient links, so clinicians must have access to every affected patient; otherwise an administrator must make the edit. The caregiver registry and account directory are organization-scoped staff resources.

Unauthorized users cannot bypass these rules through API calls. Cross-tenant patient identifiers return 404; same-tenant patients without a valid assignment/grant return 403. Inactive accounts or organizations cannot authenticate. Inactive patient profiles remain available as historical records to users who still have permission.

## Patient profile

Required: name, international WhatsApp number, active treating doctor. Month/year of birth may both be unknown; if provided they must be paired, valid, and not in the future. Other fields: sex, address, family physician, preferred pharmacy, clinician-entered baseline/diagnosis notes, IANA timezone and active/inactive status.

Patient 360 shows profile, active clinical team, caregiver links, and onboarding history. Caregivers see their own caregiver link rather than other caregivers' contacts or permission history. Empty monitoring panels state that no active care plan or readings are recorded.

## Caregiver access

1. Register a caregiver contact, optionally binding a local CAREGIVER account.
2. Link the registered contact to an assigned patient.
3. Explicitly grant dashboard access if wanted. The default is disabled.
4. Revoke dashboard permission or end the link to immediately deny subsequent patient reads.

Contact-only caregivers can be linked without dashboard access. Account binding is unique. Changing a caregiver's bound account revokes old dashboard grants; it never transfers patient permissions automatically.

## Persistence and audit

### Patient dashboard amendment 26 September 2026

Alembic `0003_patient_dashboard` adds the PATIENT role and optional unique `Patient.dashboard_user_id` tenant-composite foreign key, preserving existing M1 records. Administrators use Patient 360's Patient dashboard account section to bind or remove an active same-tenant PATIENT account. Binding/rebinding/revocation is version-checked and audited. Doctors/PAs, caregivers and patients cannot alter account ownership. Production identity verification is later work.

Demo Patient A and Demo Patient B identities read only their matching records. Demo Unlinked Patient has no access. The patient landing page is My health dashboard, without the multi-patient registry, caregiver contacts/permissions or editing tools. Patient history includes profile and care-team changes, with account administration and caregiver events omitted. The clinical panels remain empty until later milestones provide data. Seed initializes demo ownership once; it never restores a revoked/replaced patient binding.

Downgrade refuses to silently delete PATIENT accounts or change their roles. Existing patient accounts must be deliberately migrated/archived before reverting to the previous role schema.

Alembic revision `0002_m1_onboarding` adds four tables and tenant-composite constraints. Existing M0 data is preserved. Memberships retain start/end timestamps; relinking preserves the old row. UUIDs and timezone-aware timestamps are used throughout.

Every create, actual profile change, team/link change and permission change appends an audit event with actor, organization, optional correlation, and before/after values in the same database transaction. Failed validation, denied access, stale writes, and duplicate no-ops do not append misleading mutation events.

Patient rows serialize patient/membership writes; caregiver profile/account edits lock the caregiver and affected patients in consistent order. Each write requires the relevant record version. A conflict returns 409 instead of overwriting another edit.

## Local startup

`docker compose up --build` starts the stack, applies migrations and creates missing synthetic seed records. Home: port 3000. Host API: port 8030, mapped to container 8000. `/diagnostics` preserves M0 readiness and diagnostic actions. The stable Compose project name preserves existing volumes. Development authentication remains local scaffolding, not production authentication.

## Acceptance

Create/edit a synthetic patient; assign doctor/PA; register/link a caregiver; demonstrate that a link alone grants no dashboard access; grant access; switch to the caregiver and see only the permitted patient; revoke access and confirm denial; bind a patient identity and show only its own details/history; deny patient writes and other-patient reads; revoke/rebind ownership; verify timeline/audit, duplicate safety, conflicts, tenant boundaries, migrations, seed reruns and restart persistence. Automated tests and browser results are recorded in `M1_TEST_REPORT.md`.
